# Call Relay audio fix — 2026-09-05

## Evidence and changes

The saved staging test on September 4 at 19:53 UTC connected both endpoints
using host/UDP candidates. iPhone summaries increased to 383,159 bytes sent and
196,383 received, with RTT mostly 6–16 ms. This demonstrates bidirectional RTP
transport, not audible speech. No evidence required a Worker or TURN change.

Android's external WebRTC processors were treating Float32 memory as PCM16.
The m144 JNI callback exposes `float*` with `sizeof(float)` bytes per sample,
and `AudioBuffer` uses FloatS16 amplitude (approximately -32768…32767), not
normalized -1…1. Both gain processors now use Float32 and the actual frame
count. Applying the default 1.35 playback gain to two-byte halves corrupted
samples and could falsely activate the return-path echo gate. Existing acoustic
echo guarding and listen/talk modes remain enabled; no blind gain boost was added.

Sources:

- [m144 JNI buffer implementation](https://github.com/webrtc-sdk/webrtc/blob/m144_release/sdk/android/src/jni/pc/external_audio_processing_factory.cc)
- [m144 audio processor callback](https://github.com/webrtc-sdk/webrtc/blob/m144_release/sdk/android/src/jni/pc/external_audio_processor.cc)
- [m144 FloatS16 conversion](https://github.com/webrtc-sdk/webrtc/blob/m144_release/modules/audio_processing/audio_buffer.cc)

iPhone now configures play-and-record/voice-chat before fulfilling CallKit
start/answer actions, following [Apple's CallKit integration sequence](https://developer.apple.com/documentation/callkit/making-and-receiving-voip-calls).
Only real CallKit activation/deactivation callbacks notify WebRTC. Peer teardown
disables its audio without falsely deactivating the externally owned session.
Rebuilding a peer preserves activation, mute and listen/talk state. Bluetooth
uses a call-capable route rather than requesting playback-only A2DP.
Cancelled setup timers and stale peer callbacks/answers are guarded during recovery.

Android logs numeric audio windows under `RelayAudio`: pre-gate capture,
post-gate capture, playback, gate count, capture-silenced status, packet bytes
and media volume. The relay screen also shows the level summary. iPhone's
active-call screen has an **Audio diagnostics** button showing track enables,
CallKit activation, levels/energy, routes, output volume and packet counters.
No conversation audio is saved or uploaded. Diagnostic fields are local; the
existing cloud media-summary payload remains compatible.

## Install on the Mac

1. Copy `CallRelay-audio-fix-2026-09-05.zip` to the Mac and double-click it.
2. Close the project in Xcode.
3. In Terminal, run (adjust the extracted folder if necessary):

   ```bash
   bash ~/Downloads/CallRelay-audio-fix-2026-09-05/apply-audio-fix.sh ~/Documents/CallRelay
   ```

4. The script backs up seven existing Swift files inside the project before
   replacing them. It does not change Firebase configuration, signing team,
   icons, entitlements or the generated project. Preserve the backup if you
   have additional Mac-only source edits; compare/reapply those edits as needed.
5. Reopen `CallRelay.xcodeproj`, select the connected iPhone and press Command+R.
   No XcodeGen regeneration is needed. Run Command+U against an installed
   compatible simulator to execute tests; hardware voice testing is separate.

To undo the source update, copy the seven files from the printed backup folder
back to their matching paths. No files are deleted by the installer.

## Android and physical retest

The updated staging debug APK is version **0.7.1-audio-fix**, version code **8**.
Install it as an update (`adb install -r <apk>`); do not uninstall the existing
app or clear its data, because that removes stored authentication/pairing.
No connected Android or remotely accessible Mac was available for installation
and physical retesting during this fix.

After BOTH updated builds are installed:

1. Keep Android's relay/accessibility service enabled and confirm both devices
   use staging and the existing pairing.
2. With both devices unlocked, choose Full duplex and unmute. Begin a normal,
   consented test call. Keep iPhone away from Android so their speakers do not
   form an extra feedback loop.
3. Have the third-phone person speak alone for ten seconds, then the iPhone
   person speak alone for ten seconds. Check intelligibility in both directions.
4. Open iPhone Audio diagnostics. If transport bytes rise but received energy
   stays zero, inspect Android pre/post-gate levels and capture-silenced status.
   If received energy rises but the iPhone is silent, inspect its enabled receive
   track, route and volume. `Unavailable` means the SDK omitted a statistic,
   not a measured zero.
5. Test overlapping speech, Listen/Talk fallback, mute/unmute, speaker/receiver,
   Bluetooth, lock during an active call, and a second call after hangup.
6. For five-minute and network-transition tests, confirm no unexpected teardown
   and save `adb logcat -d -s RelayAudio:I` plus iPhone diagnostic screenshots.
   This filtered log contains levels/state, not recordings.

This remains a stock-Android **acoustic** cellular bridge, not privileged digital
SIM-audio capture. Firmware capture restrictions, speaker/microphone coupling,
volume and simultaneous speech still require handset testing. A passing build
does not prove reliable end-to-end full-duplex carrier audio.
